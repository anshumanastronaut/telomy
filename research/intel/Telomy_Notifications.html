Part A — What exists today

Telomy has one notification surface: a pull-model, in-app-only list. No stored record, no delivery, no channel beyond the app screen.

The list that exists

features.py:159 notifications() recomputes on every request — 6 patient kinds: shared_doc, retest, review, insight, appointment, medication. Served at /notifications; read-state is a dedup set only (notif_read, key kind:title) — no row, timestamp, channel or audit.

Channels: in-app only

Exhaustive grep for any email/SMS/WhatsApp/push sender returns zero. No expo-notifications, no push tokens. OTP is stubbed (000000). Appointment booking says "confirms by SMS" but sends nothing.

Infra exists but inert

interop.py has outbound webhooks (HMAC-signed fire()) + FHIR R4 export — but fire() has no callers. The "notify an external EHR on a result" plumbing is built and never triggered.

Consent yes, prefs no

8 DPDP purposes modeled (incl. a separate marketing opt-in). But no per-category / per-channel / quiet-hours preference model. Staff side has coarse booleans with no delivery behind them.

Inbound = PDF only

Lab reports parse from PDF (labparse.py). No EML / email / CSV / inbound-HL7 path. Device inbound (WHOOP, CGM, patch) is telemetry, not reports.

No safety tier

Marker status is whatever the client sends or "unknown". No critical/panic tier, no auto-flag on ingest, no safety alert.

Part B — Benchmarks & India rules

Secondary sources (vendor docs, law-firm/BSP summaries). Verify DLT/WhatsApp specifics on the live Meta & operator portals, and DPDP against the notified Rules, before build.

Consumer labs (Function / Superpower)

Every value flagged in/out of range; clinician review framed as "talk to a clinician," never a diagnosis. Results come with context + a next step, never a bare "you're abnormal" push — the pattern our clinician_notes + review queue already mirrors.

Wearables (Oura / Whoop)

One morning Readiness/Recovery push; anomaly nudges (elevated resting HR, temp); missing-night & sync reminders; streaks. Batched to a daily summary, not per-metric spam. We already compute the equivalents — just don't deliver them.

India channel strategy

WhatsApp is a primary report/appointment channel (Apollo 24|7, Tata 1mg, Practo, Eka Care) alongside SMS + push, because open rates dwarf email. Stack: SMS (DLT) for OTP/must-deliver, WhatsApp utility for reports/appointments, push for engagement, email for records/PDFs.

Critical-value alerting (safety)

Accreditor norm (CAP / Joint Commission, secondary): ≥90% of critical values reported within ~30 min; closed-loop read-back documented; recipient a licensed caregiver; an escalation policy for non-ack.

Part C — The notification matrix

Priority tiers & defaults: CRITICAL push+SMS+WhatsApp, bypass quiet hours, closed-loop ack, vital-interest basis — never the clinical value on a lock screen. HIGH push primary, WhatsApp fallback if unread, quiet hours except time-sensitive. NORMAL in-app+push, batched, quiet hours honored. LOW opt-in engagement, digest, quiet 21:00–09:00 IST, unsubscribe. Every category has a per-channel toggle except safety and OTP/security (always on).

Part D — Inbound report flows

Principle: ingest → normalize → persist → auto-flag → notify, with the notify tier decided by the auto-flag. Today only the PDF path exists and it stops at persist.

1 · PDF upload (built)

/labs/parse_b64 → confirm markers → /labs/save. Add the auto-flag step on save, then emit U1/U3/U4 (+ D5/D1 for panel patients).

2 · Email ingestion (build)

Per-user address reports+<token>@in.telomy.health + shared clinic inbox. Provider inbound route → POST /ingest/email. Verify SPF/DKIM + allow-list; else a review queue. MIME walk → PDF/CSV/EML/FHIR dispatch → auto-flag → U1.

3 · EML / forwarded email (build)

Same MIME walker, uploaded as a file via an extended /documents/parse. For "patient forwards the lab's email" — parse the nested message/rfc822 and recurse.

4 · CSV (build)

Columns → markers map (test, value, unit, ref range, date). Bulk/historical import & lab portals. Same auto-flag + U1.

5 · HL7 v2 / FHIR R4 inbound (build)

We already export FHIR; add inbound POST /interop/fhir + an HL7 ORU^R01 adapter, authed by existing scoped API keys. The clean B2B lab-integration path.

6 · Device APIs (built, keep distinct)

WHOOP, cal, Nightscout CGM, vitals, Apple Health are telemetry, not reports — they feed U18–21 & the score, not U1/U4. Keep the critical tier scoped to lab markers.

D.2 · Critical-value auto-flagging (new, patient-safety)

A deterministic step on every ingest path before notifying: compare each marker to its reference range and a new critical/panic threshold table (K⁺, Na⁺, glucose, Hb, platelets, WBC, creatinine, troponin, calcium, INR). Add a critical status. Tier → critical: U4+D1(+C1); out_of_range: U3; else U1. Record provenance for audit + the ack log. Reuse the inert interop.fire('lab.result') to notify subscribed EHRs.

Safety copy rule. The patient notification never states the dangerous number on push/SMS — "an important result needs attention, open Telomy." The doctor alert carries the clinical value, because a licensed caregiver is in the loop.

Part E — Architecture & roadmap

No queue/worker, fragile box → do not add Celery/Redis. Store, generate by cron, deliver by thin provider calls, keep the critical path synchronous.

① Notification store

Real table notifications(…, created_at, read_at, dedup_key, channels_json, delivered_json, ack_at). Builders write rows (idempotent on dedup_key) instead of recomputing; notif_read → read_at.

② Generation = cron

A lightweight cron (how backups already run) scans triggers every few minutes, inserts rows + enqueues sends into a SQLite notif_outbox. Mirrors the mobile outbox; survives restarts.

③ Delivery = thin calls

A second cron drains the outbox, calling provider HTTP APIs with short timeouts (like interop.fire's 5s urllib), marking delivery per channel, retrying with backoff. No persistent connections.

④ Critical path synchronous

U4/D1/C1 fire inline on ingest, open a closed-loop ack record; a cron sweep escalates unacked critical alerts (doctor → centre) per SLA.

Channel adapters

Push — expo-notifications + token registration, send via the Expo Push API (single HTTPS endpoint, no SDK on the box — cheapest for the micro); local scheduled for dose reminders. Email — SES/Postmark + SPF/DKIM/DMARC on telomy.health; inbound route for /ingest/email. SMS — DLT-registered Indian BSP (MSG91/Gupshup/Kaleyra), templates for OTP, reminders, critical "open app," billing failure. WhatsApp — Business via BSP with approved utility/auth templates + opt-in capture; 24h window for free-form consult replies.

Open risks to settle before build

  • Patient-safety posture. Telomy is positioned as wellness ("not a diagnosis"). Decide whether we assert criticality (clinical liability, needs licensed-clinician loop) or route to a clinician without asserting. Recommendation: route for patient-facing copy; assert only on the doctor/centre safety path.
  • Threshold ownership. The critical/panic table needs clinical sign-off (age/sex-specific, India reference ranges) — not an engineering decision.
  • Box capacity. If synchronous critical sends + digests strain the 512MB box (the known wedge), move the delivery cron to a tiny separate process / managed function; keep FastAPI doing only inline critical sends.
  • Regulatory, verify primary: CAP/Joint-Commission timeframe & read-back wording; DPDP Rule-4 date (~13 Nov 2026) & SDF status at our scale; TRAI header-suffix scheme; WhatsApp 24h-window mechanics & template SLAs.
