# Telomy — Full System Audit (2026-10-20)

Auditor + software-tester pass over everything built to date. Each finding below was **verified** (empirical test, code trace, or live check), with severity, evidence, and the fix direction. Nothing here is fixed yet — this is for review, then we fix.

**Baseline health:** backend test suite **180 passed**; all modules import; console JS parses; iOS Release builds & installs; no `NotImplementedError`/`...` stubs; the 57 "stub/placeholder" grep hits are all UI `placeholder=` props and citations (not real stubs). SQL built with f-strings interpolates only code constants — user values are parameterized (no injection).

## 🔴 CRITICAL — security, must fix before any multi-user / public use

### C1. The management plane (`/mgmt/*`) is UNAUTHENTICATED in multi-user mode
**Verified.** The `_require_password` middleware returns early when `acctmod.enabled()` (multi-user), and the `_bind_user` dependency explicitly skips `/mgmt`. Most `/mgmt` endpoints have no per-endpoint guard, so once any consumer account exists (multi-user turns on automatically), the entire management surface is open with **no token**:

| Request (NO token, multi-user) | Result |
|---|---|
| `GET /mgmt/centre/members` | **200** — member/patient PII |
| `GET /mgmt/clinic/inbox` | **200** — clinical data |
| `GET /mgmt/catalog`, `/mgmt/api-keys` | **200** |
| `POST /mgmt/api-keys` | **200 — minted a working API key** |
| `POST /mgmt/clinic/patients/1/notes` | **200 — forged a clinical note** |
| `POST /mgmt/catalog` | **200 — injected catalog data** |

(Consumer Vault is correctly locked: `GET /today` without a token → 401. So the *management* plane has weaker auth than the consumer plane — backwards.)
**Fix:** require a valid staff token for every `/mgmt/*` route (a single dependency on the mgmt router, not per-endpoint), independent of consumer multi-user mode. The production cloud is single-user today so it's gated *now*, but this opens the moment multi-user is enabled — and the platform's whole point is multi-user.

### C2. No cross-tenant authorization — any staff can read/write any centre's data
**Verified.** An `orgA` `centre_admin` token called `GET /mgmt/billing/summary?org=orgB` → **200**. Most `/mgmt` endpoints trust the `org=` query param without checking it against the caller's org. A centre's staff can read another centre's patients, revenue, billing and payments, and act on them, just by changing `org=`. `_require_org_admin` is only on a handful of mutating routes; reads and many writes use `_require_staff` (any token) or nothing.
**Fix:** derive `org` from the authenticated staff (`me["org"]`) instead of the query param; a super-admin may pass an explicit org. Enforce on every org-scoped route. `billing.record_payment` similarly should verify the invoice belongs to the caller's org.

## 🟠 HIGH — platform/ops, blocks the "everything on cloud" goal

### H1. The cloud server runs OLD code — the platform isn't deployed
**Verified** (`ssh … ls app/`): the Oracle box has **no `tenancy.py`, `billing.py`, or `staff.py`**, and `grep mgmt/admin/overview` = 0. The cloud only runs the consumer app + WHOOP push. So the doctor/centre/super-admin consoles, the care graph, and billing exist **only on the Mac**. Before moving the mobile app (or anything) to the cloud, the current code must be deployed there — and fixing C1/C2 first is mandatory, since deploying the platform to a public server without them would expose everything.

### H2. No backups, no process supervision for the Mac backend
The Mac backend is a manual `nohup uvicorn …`; **no launch agent, no auto-restart, no backup** of `telomy-live.db` (now **367 MB** of real study data). A reboot or crash takes it down silently with no recovery, and the data exists in exactly one place. The cloud has systemd but old code.
**Fix:** a `launchd` plist (keepalive) on the Mac and a periodic `sqlite3 .backup` to a second location; and/or make the cloud the system of record.

### H3. Data + code are split across two diverging sources of truth
WHOOP now exports to the **cloud** (`/opt/telomy/telomy.db`, ~1.5 M rows); patch/ring + the whole platform + last night's data live on the **Mac** (`telomy-live.db`). The two DBs and two code versions are diverging. NOOP also shares one `receiverStateId` between them, so it can't treat them as distinct receivers.
**Fix:** pick one system of record (recommended: the cloud, once C1/C2 fixed and platform deployed), point all devices there, and migrate the Mac's historical data in.

### H4. Mobile doctor/centre views are demos, not wired to the platform
The app's own copy says "the doctor and centre views are demos for now." They read the legacy `roles.py` identity (e.g. "Dr. Meera Rao", `accounts`/`patients`), which is a **separate identity system** from the new `staff`/`tenancy` backend. So the 500-patient network and the real care graph can't be driven from the phone. This is the identity bridge still outstanding from earlier.

## 🟡 MEDIUM — reliability, correctness, coverage

- **M1. Device sync fragility (LAN).** Documented the hard way last night: Mac LAN IP churns (192.168→10.204→172.20 hotspot), the iPhone hotspot is Android-metered (NOOP refused it), and NOOP rejects `.local` names. Mitigated now (Bonjour for the app, cloud for WHOOP, USB reverse-tunnel as a fallback) but the LAN path remains brittle. The cloud path (H1/H3) is the real fix.
- **M2. Ring flapping.** Connect/disconnect loop wrecked the ring's overnight capture (213 samples, quit ~02:05). The reconnect code is the correct iOS pattern, so the cause is physical (battery / a competing app holding the single BLE slot). The app offers **no low-battery warning, no "another device is connected" hint, and no reconnect backoff/health indicator** — add these so the user isn't flying blind.
- **M3. SpO₂ gating untested.** The new awake-≥90 / overnight-≥80 plausibility gates (KYRing.swift) ship **with no unit test**, and the thresholds are heuristic. Add a decode test over sample frames incl. the known garbage values (54–146).
- **M4. Silent error swallowing.** ~16 broad `except … : pass`-style handlers can hide failures. Audit each; at minimum log. (No fake/stub implementations found — good.)
- **M5. Single shared secret spans planes.** The access-password-derived `_token()` also authorizes `/mgmt`. Management and consumer auth should not share one secret.
- **M6. Test-coverage gaps.** No tests for: authz/multi-tenant isolation (would have caught C1/C2), the console SPA, the native ring/patch modules, or billing *endpoints* (only unit-level billing is tested).

## 🟢 LOW — polish / hardening

- **L1. Staff tokens never expire** (live until explicit logout). Add TTL/rotation.
- **L2. WHOOP token ops.** It was lost on a restart because it lived only in a shell env; the study token currently sits in `/tmp/telomy-study-env.txt`. Put it in the persistent env file (Mac) — the cloud already has it in `/etc/telomy.env`.
- **L3. Simulation vs real data.** Synthetic rows carry `is_test_data`, but verify the 500-patient simulation DB is never the one serving real device data (it was briefly a `/private/tmp` scratchpad; now on `telomy-live.db`).

---

## Suggested fix order (for discussion)
1. **C1 + C2** (auth + tenant isolation) — nothing else ships publicly until these are closed; add the authz tests from M6 alongside.
2. **H1** deploy current code to cloud; **H2** backups + keepalive.
3. **H3** consolidate on the cloud as system of record; **H4** bridge mobile identity → then move patch/ring to cloud (the original request).
4. **M1–M6**, then **L1–L3**.
