# From test user to real users: the production plan

**Status:** v0.4 prototype → v1.0 production · **Owner:** engineering lead · **Last reviewed:** 2026-10-11

Telomy v0.4 was built and verified with one fictitious member ("Aarav, Test User"), a synthetic doctor panel and a synthetic
longevity centre. This document is the step-by-step plan to run the same product for real members, doctors and centres:
what is static today, what must change, in what order, and how we know each step is done.

Read with: [HLD](../architecture/HLD.md) (target architecture) · [LLD](../architecture/LLD.md) (module detail) ·
[SECURITY_PRIVACY](../SECURITY_PRIVACY.md) · [CLINICAL_SAFETY](../CLINICAL_SAFETY.md) ·

## 1. What is static or single-user today (audit, 2026-10-11)

| Area | Today (v0.4) | Why it blocks production |
|---|---|---|
| **Tenancy** | 48 tables; only 5 carry `patient_id` (`bookings`, `clinical_notes`, `rx_plans`, `therapy_plans`, `therapy_sessions`). The member Vault (`signals`, `results`, `reports`, `events`, `insights`, …) holds **one person**. `profile` and `subscriptions` are `CHECK (id = 1)`. | Two real users would see each other's data. |
| **Doctor panel / centre members** | `patients` rows are summary cards (`data` JSON of risk inputs) generated by `roles.seed`; only patient 1 has a full Vault. | Panels must be built from real members' Vaults. |
| **Identity** | `POST /auth/otp/verify` accepts the fixed code `000000`; no sessions, no tokens; the app picks a role on the welcome screen. | Anyone can act as any role. |
| **Authorisation** | No per-route checks. `POST /admin/reset` wipes and reseeds the DB with no auth. Only device-key routes check `X-Admin-Key` / `X-Device-Key`. | Data exposure and destructive endpoints. |
| **Clock** | `TELOMY_TODAY` pins "today" (2026-10-06); `engine.now_iso()` = last signal day + wall time. | Real users live in real time. |
| **Data** | `seed.py` builds a fictitious Vault with planted effects (ground truth for tests); 24 synthetic lab PDFs; simulated therapy traces (labelled "simulated (ODE prior)"). | Real data arrives empty, sparse and messy. |
| **Database** | SQLite file (`TELOMY_DB`), schema created in code (`CREATE TABLE IF NOT EXISTS`), no migrations. | No concurrency, backups, migrations or time-series scale. |
| **Files** | Lab PDFs parsed in memory; documents stored as rows. | Need object storage, retention, malware scanning. |
| **Background work** | Insights, summaries and twin calibration run inside requests. | Real Vaults need scheduled and event-driven jobs. |
| **Drug interactions** | Curated rules + DDInter (CC BY-NC-SA, **non-commercial**, git-ignored). | Must be replaced by a licensed source before charging anyone. |
| **Payments** | Test mode only. | Live Razorpay + GST invoicing. |
| **Hosting** | Mac + Cloudflare quick tunnels for demos (`demo.db`, random admin key). | Not a production environment. |
| **LLM** | Claude when `ANTHROPIC_API_KEY` is set, else the grounded composer. | Needs a production key, a data-processing agreement, PHI-minimised prompts and logging rules. |

What is **already production-shaped** and is kept: the catalogue of 221 markers with zones and evidence grades; validated risk models
(PREVENT 2024, PCE, ADA, FIB-4, KFRE); the statistics (adjusted effects, Benjamini–Hochberg, split-half replication, minimum-event
thresholds); the physiology priors validated against 11 literature targets; the device API with per-device SHA-256 keys and channel
limits; the draft → clinician-sign workflow; consent purposes; provenance on every value; 117 automated tests.

## 2. Target state (v1.0)

Per *Engineering Guide v3.0*, adapted to what the prototype proved:

- **Identity:** phone OTP (Twilio/Exotel/MSG91) → JWT access token (30 min) + rotating refresh token (30 days). Clinicians add TOTP
  and a verified registration (NMC / state council number). Centre staff belong to an organisation.
- **Tenancy:** every member-owned row has `user_id`; every org-owned row has `org_id`. Postgres Row-Level Security enforces it as a
  second line behind application checks. Doctors and centres see a member only through an active `care_relationship` **and** the
  member's consent for that purpose.
- **Consent:** every request carries `x-purpose` (`self` · `clinician` · `centre` · `research`); the consent service is the gate.
  DPDP data-subject requests (export, correct, delete) are self-serve.
- **Data:** Postgres 16 + TimescaleDB (signals, telemetry, events as hypertables partitioned by `user_id`), S3 (PDFs, DICOM, audio
  never stored), Redis (rate limits, job queue). All in **AWS ap-south-1 (Mumbai)** for DPDP residency; nightly encrypted backups to
  ap-south-2 (Hyderabad). RPO 15 min / RTO 1 h.
- **Services:** start as **one FastAPI service with clear modules** (today's layout) plus a worker process. Split into the eight services
  of the Engineering Guide only when team size or load requires it.
- **Clients:** the existing Expo app (one binary, three roles), shipped through EAS Build → TestFlight / Play internal testing → stores.
- **Observability:** structured PHI-redacted logs, metrics, traces (OpenTelemetry), Sentry; audit log of every read of another person's data.

## 3. Step-by-step migration

Each phase ends with an exit check. Do them in order; phases 1–3 can overlap across two engineers.

### Phase 0 · Freeze and harden the prototype (1 week)

1. Tag `v0.4-prototype`; keep `seed.py`, `demo.db` and the test suite as the **fixture world** (tests and demos keep using them).
2. Add `TELOMY_ENV` = `local | ci | dev | staging | prod`. In `staging`/`prod`:
   - refuse to start if `TELOMY_TODAY` is set, if `TELOMY_ADMIN_KEY` is the default, or if DDInter files are present;
   - do not register `/admin/reset`, the OTP dev code, or seed-on-empty-DB in the lifespan hook.
3. Move secrets to AWS Secrets Manager; `.env` stays for local only.
4. Add CORS allow-list, request size limits (PDF ≤ 20 MB), and rate limits (100 req/min/user, 10/min for Sinc).

*Exit:* `TELOMY_ENV=prod` boots with no seed and no dev routes; a test asserts each refusal.

### Phase 1 · Identity, roles and tenancy (3–4 weeks), the critical path

1. **Schema:** add `users` (id UUID, phone, email, status), `orgs` (centres, clinics), `memberships` (user ↔ org ↔ role:
   `member | clinician | centre_owner | centre_staff | admin`), `care_relationships` (clinician/org ↔ member, status, purposes),
   `sessions` (refresh tokens, device), `audit_log`.
2. **Ownership column on every table.** Mapping (verify against `docs/DATA_MODEL.md` when implementing):

   | Owner | Tables |
   |---|---|
   | `user_id` (member data) | `profile`, `signals`, `results`, `reports`, `documents`, `imaging`, `events`, `meals`, `medications`, `med_doses`, `insights`, `review_thread`, `memories`, `chats`, `messages`, `studies`, `routines`, `routine_log`, `activity_types`*, `activity_sessions`, `voice_samples`, `exposure`, `consents`, `consent_history`, `shares`, `access_log`, `notif_read`, `checklist`, `subscriptions`, `monthly_reports`, `consults`, `appointments`, `report_reviews`, `rx_orders`, `sessions_log` |
   | rename `patient_id` → `user_id` | `bookings`, `clinical_notes`, `rx_plans`, `therapy_plans`, `therapy_sessions` |
   | `org_id` (centre data) | `services`, `devices`, `device_keys`, `telemetry` (+ `session_id` link to a member's session) |
   | replaced | `accounts` → `users` + `memberships`; `clinicians` → `users` with clinician profile; `patients` → a **view** over members of an org |
   | global catalogue (no owner) | `protocols` (marketplace templates; a member's adoption is a `user_id` row) |

   \* `activity_types` holds both built-in templates (global) and member-created types (`user_id`).
3. **Request context:** a FastAPI dependency `current_principal()` decodes the JWT and returns `{user_id, roles, org_ids, purpose}`.
   Every route declares who may call it: `Depends(member)`, `Depends(clinician_of(user_id))`, `Depends(centre_staff_of(org_id))`.
4. **Engine functions take the subject explicitly.** Change module functions from implicit single-user (`engine.latest()`) to
   `engine.latest(user_id)`; `db.rows/one/exec_` stay thin, and queries always include `user_id = ?`. Do it module by module with
   the tests as the safety net (the fixture world becomes user `00000000-…-0001`).
5. **Postgres RLS** on every owned table: `USING (user_id = current_setting('app.user_id')::uuid OR app_has_access(user_id))`.
6. **Mobile:** replace the role picker with sign-in (phone → OTP → role chosen from memberships); store tokens in SecureStore; attach
   `Authorization` and `x-purpose` in `lib/api.ts`; handle 401 → refresh → re-login.
7. **Doctor panel and centre members** read from real `care_relationships`; risk cards computed from each member's Vault
   (`roles.patient_card` becomes a per-user query, cached).

*Exit:* a test creates two members, one doctor linked to member A only, and one centre: every endpoint returns only what that
principal may see (403/404 otherwise); RLS blocks a deliberately unscoped query.

### Phase 2 · Real data in (4–6 weeks, parallel to Phase 3)

1. **Empty-Vault experience:** onboarding (profile, consents, connect a wearable, upload first report); every screen has a designed
   empty state; engines return `too_early` rather than numbers when below thresholds (they already do for therapies and activities;
   audit Home, twin and predictions).
2. **Clock:** `now_iso()` becomes real UTC time stored with the member's timezone; "today" is the member's local date.
3. **Lab reports from any lab:** keep the text parser; add OCR (AWS Textract) for scanned PDFs; unit and alias normalisation is already
   in `catalog*`; anything unmatched or low-confidence goes to a **human review queue** before it enters the Vault. Partner-lab APIs
   (Redcliffe, Healthians, Tata 1mg, PathKind, Vijaya per DPR §5.1) later.
4. **Wearables:** HealthKit and Health Connect (native modules, requires the dev build already used), then Oura/Whoop/Garmin OAuth,
   Dexcom/Libre CGM. Each sample keeps `source` and `device` for provenance.
5. **Centre machines and the Telomy patch:** issue device keys per org; machines stream to `/devices/{id}/telemetry` (or the MQTT
   bridge); the patch uploads RR intervals and SpO₂ to `/therapy/sessions/{id}/samples` (already built). Sessions switch from
   "simulated" to "measured" automatically when samples exist.
6. **Exposome:** member's city from profile and, with consent, coarse location; Open-Meteo/CAMS calls cached per city per day.
7. **Voice:** Whisper runs on a worker (GPU optional); raw audio is deleted after transcription (already the rule).

*Exit:* a new real account with only Apple Health + one lab PDF gets a correct, honest Home within 10 minutes, and nothing on screen
is synthetic.

### Phase 3 · Infrastructure (3–4 weeks)

1. Terraform for AWS ap-south-1: VPC, RDS Postgres 16 + TimescaleDB (or Timescale Cloud in Mumbai), S3 (SSE-KMS), ElastiCache Redis,
   ECS Fargate (api, worker), ALB + WAF, Secrets Manager, CloudWatch → Grafana.
2. **Migrations:** introduce Alembic; the first migration reproduces today's schema plus Phase 1 columns; a one-off script ports the
   fixture world into staging.
3. **Workers:** parsing, OCR, nightly engine run per member (insights, correlations, twin calibration, monthly reports), Whisper,
   notifications. Idempotency keys on `POST /events` and orders.
4. **CI/CD:** existing GitHub Actions (pytest + tsc) + lint, security scan, Docker build, deploy to dev on merge, staging on tag,
   prod with manual approval. Mobile via EAS Build and EAS Update channels per environment.
5. **Observability and DR:** dashboards for golden signals; alerts; backups tested monthly by restore.

*Exit:* staging runs the full app from a clean deploy; restore from backup proven; p99 Vault write < 150 ms.

### Phase 4 · Compliance and clinical governance (runs from week 1, gates launch)

1. **DPDP Act 2023 + Rules:** Data Fiduciary registration of responsibilities; DPO appointed; per-purpose consent records (built) wired
   to enforcement; DSR endpoints (export, erase); breach runbook (72-hour notice); joint-fiduciary agreements with partner centres.
2. **Clinicians:** verify registration before granting the clinician role; Telemedicine Practice Guidelines 2020 for consults and
   e-prescriptions (drug list rules, identity of prescriber on the PDF, which `rx.prescription_pdf` already prints).
3. **Medical-device status:** written regulatory opinion (DPR §21 item 2) on whether risk prediction and therapy verdicts are SaMD
   under CDSCO; keep the claims firewall (*CLINICAL_SAFETY.md*) until then.
4. **Licensed drug-interaction database** replaces DDInter (e.g. a commercial licence from a vendor such as Medi-Span, First Databank
   or an Indian formulary provider; evaluate).
5. **Supplements/IVs:** FSSAI for Telomy Formulas; IV therapy only through licensed clinical establishments.
6. **Security:** VAPT before launch; annual pen-test; secrets rotation every 90 days.

*Exit:* legal sign-off memo, DPO sign-off, VAPT report with no open highs.

### Phase 5 · Pilot and launch (12 weeks, per DPR §20)

1. Closed pilot: **50 members, 3–5 partner clinics**, 12 weeks. Primary: retention and usefulness; secondary: event logging,
   insight opens, clinician review rate, time-to-sign.
2. Therapy measurement pilot with live machine telemetry + patch in one centre; compare measured sessions to the physiology prior.
3. Weekly safety review of every alert and adverse event; monthly model review.
4. Store launch after the pilot exit criteria and an incident-free final month.

## 4. Static data inventory: keep, replace or remove

| Item | Location | Production decision |
|---|---|---|
| Marker catalogue (221), panels, zones, evidence, actions | `catalog.py`, `catalog_ext.py`, `catalog_more.py` | **Keep**, version it (`catalog_version` on every result) and move to DB tables once clinicians edit it |
| Risk-model coefficients | `prevent_coef.json`, `predict.py` | **Keep** (published equations); add version + validation tests |
| Therapy modalities, devices, contraindications | `therapy.py` (`MODALITIES`, `DEVICES`) | **Keep** as catalogue; centres configure their own devices in DB |
| Physiology priors | `physio.py` | **Keep** as prior; label "simulated" until measured data exists (already done) |
| Tests catalogue (75), prices | `diagnostics.py` | Prices become per-centre/per-lab in DB |
| Rx products, curated rules | `rx.py` | Products in DB per partner pharmacy; rules move to licensed DB |
| Plans and prices | `plans.py` | **Keep** list prices; billing via Razorpay plans |
| Fictitious member, panel, centre, sessions | `seed.py`, `roles.seed`, `therapy.seed`, `activities.seed` | **Fixtures only** (tests, demos, staging); never in prod |
| Synthetic lab PDFs | `testdata/` | Test fixtures only |
| Pinned date | `TELOMY_TODAY` | Forbidden outside local/ci |
| City data | `exposome.CITIES` | Keep; extend list |

## 5. Go-live checklist

- [ ] Phase 0–4 exit checks passed and recorded in the PR that closes each phase
- [ ] No route without an explicit access rule (a test enumerates `app.routes`)
- [ ] RLS enabled on every owned table (a test queries without context and gets 0 rows)
- [ ] Seed, dev OTP and `/admin/reset` absent in prod build (test)
- [ ] Licensed interaction DB live; DDInter removed
- [ ] Backups restored successfully in the last 30 days
- [ ] DPO, clinical director and legal sign-off on file
- [ ] Incident, breach and clinical-escalation runbooks published; on-call rota set
- [ ] App Store / Play listings with medical disclaimer and privacy nutrition labels

## 6. Estimated effort

Two backend engineers, one mobile engineer, one designer (part-time), clinical director and DPO (part-time):
**≈ 12–14 weeks to a closed pilot**, then the 12-week pilot. The critical path is Phase 1 (tenancy), because every module changes.
